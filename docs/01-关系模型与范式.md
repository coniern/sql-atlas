# 01 · 关系模型与范式：为什么表要这么切

> 一句话：关系模型把数据切成"一次事实一张表"，用键把它们缝回去。范式告诉你怎么切，反范式告诉你什么时候偷懒。

## 1.1 关系模型的三个核心概念

| 概念 | 是什么 | 在 atlas.db 里的例子 |
|---|---|---|
| 关系（表） | 一个元组（行）的集合，**行无序、不重复** | `orders` |
| 键 | 唯一标识一行的列（组合） | `order_id` 主键、`order_no` 唯一键 |
| 外键 | 指向另一张表主键的列，声明"行与行怎么关联" | `orders.customer_id` |

三个不太直观但重要的推论：

1. **行没有顺序**。`SELECT` 不带 `ORDER BY` 时返回顺序是未定义的 —— 今天是插入顺序，明天可能不是。想要顺序，永远显式写 `ORDER BY`。
2. **表没有重复行**。所以有 `DISTINCT` 的存在，所以集合运算（UNION/INTERSECT）才有意义。
3. **单元格必须是原子值**。一个格子里不能塞一个数组 —— 这就是第一范式（1NF），也是后面讲逗号分隔列反模式的伏笔。

## 1.2 范式：怎么判断表切得对不对

范式不是玄学，是三条递进的检查：

**1NF：每个格子都是原子值**

反例（你一定见过这种表）：

```sql
-- 反面教材： hobbies 列存 "篮球,编程,摄影"
SELECT * FROM users WHERE hobbies LIKE '%编程%';   -- 能跑，但索引全废，还会误伤"爱编程史"
```

问题：没法建索引、没法统计、更新一项要改整个字符串。正确做法是拆成 `user_hobbies(user_id, hobby)` 两张表。

**2NF：非主键列必须依赖整个主键（只对复合主键有意义）**

如果 `order_items(order_id, product_id, product_name, quantity)` 用前两列做复合主键，`product_name` 只依赖 `product_id` —— 这叫部分依赖。后果：产品改名，几千行明细要一起改，漏一行就数据不一致。修法：产品信息挪到 `products` 表，明细只留 `product_id`。

**3NF：非主键列之间不能相互依赖**

看 atlas.db 的真实设计决策 —— `order_items` 里有 `unit_price`，但 `orders` 里**没有**订单总额：

```
为什么 orders 不存 order_total？
答：总额 = SUM(明细)。存了它就是 3NF 违例（总额依赖明细，明细一改总额就脏）。
两个写入路径（写明细 + 写总额）永远可能不同步 —— 下单和退款并发时必出 bug。
```

结论：**派生数据不落库**（要用时算，或者用生成列/触发器维护，见 02 章）。

## 1.3 反范式：什么时候故意"违反"范式

范式不是越高越好。atlas.db 里有一处刻意的反范式：

```sql
-- order_items.unit_price：下单时的价格快照
```

产品价格天天变，但三个月前的订单账单不能跟着变。**这里存的不是"当前价格"（那才是冗余），而是"当时的价格"（历史事实）**。判断标准：

> 冗余字段如果表达的是"某一时刻的事实"而非"当前状态"，它就不是冗余，是历史记录。

## 1.4 用真实库检验一遍

```sql
-- 看看 orders 表为什么"瘦"：除了状态和时间，没有任何客户/商品信息
SELECT name FROM pragma_table_info('orders');
```

```
┌─────────────┐
│ name        │
├─────────────┤
│ order_id    │
│ order_no    │
│ customer_id │   ← 只有 id，姓名要去 customers 表拿
│ employee_id │
│ status      │
│ ordered_at  │
│ shipped_at  │
│ note        │
└─────────────┘
```

代价是什么？查一个订单要 JOIN 两三张表。收益是什么？客户改名只改一行。**范式 = 读时多 JOIN，写时零不一致；反范式反之**。读多写少且要强一致的订单系统选前者，读多写少但查询极慢的报表场景选后者（第 10 章细讲）。

## 1.5 三张自引用表：atlas.db 的彩蛋

```sql
SELECT name,
       (SELECT name FROM categories p WHERE p.category_id = c.parent_id) AS 父品类
FROM categories c
WHERE c.parent_id IS NOT NULL LIMIT 4;
```

```
┌────────┬──────────┐
│ name   │ 父品类   │
├────────┼──────────┤
│ 手机   │ 电子产品 │
│ 电脑   │ 电子产品 │
│ 音频   │ 电子产品 │
│ 配件   │ 电子产品 │
└────────┴──────────┘
```

`parent_id` 指向自己表的主键 —— 树形结构的标准存法。但你也注意到了：**查一层要一个子查询，查整棵树要递归**（第 7 章专门解决）。

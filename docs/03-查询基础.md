# 03 · 查询基础：SELECT 的完整语法和 NULL 的陷阱

> 一句话：SELECT 的子句有严格的执行顺序，NULL 有一套独立的三值逻辑。这两件事搞反了，写出来的查询"看起来对，结果是错的"。

## 3.1 子句的书写顺序 ≠ 执行顺序

```sql
SELECT   status, COUNT(*)            -- ⑤ 输出列
FROM     orders                      -- ① 先拿到数据源
WHERE    ordered_at >= '2024-01-01'  -- ② 行级过滤（此时还没有分组！）
GROUP BY status                      -- ③ 分组
HAVING   COUNT(*) > 100              -- ④ 组级过滤
ORDER BY 2 DESC                      -- ⑥ 排序（可以用列序号）
LIMIT    5;                          -- ⑦ 截断
```

**为什么 `WHERE` 里不能写 `COUNT(*)`，`HAVING` 里可以？** 因为执行到 WHERE 时还没有分组、聚合根本没发生。这不是语法规定，是执行顺序的自然结果。同理：**SELECT 里起的别名，WHERE 里用不了，HAVING/ORDER BY 里可以用**（有的数据库允许，但那是方言糖，别依赖）。

## 3.2 聚合与分组

跑一遍真实数据（3000 单的分布）：

```sql
SELECT status, COUNT(*) AS n,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM orders), 1) AS pct
FROM orders GROUP BY status ORDER BY n DESC;
```

```
┌───────────┬──────┬──────┐
│ status    │ n    │ pct  │
├───────────┼──────┼──────┤
│ shipped   │ 1311 │ 43.7 │
│ paid      │ 1088 │ 36.3 │
│ pending   │  261 │  8.7 │
│ cancelled │  231 │  7.7 │
│ refunded  │  109 │  3.6 │
└───────────┴──────┴──────┘
```

三个容易忽略的细节：

1. **`COUNT(*)` 和 `COUNT(列)` 语义不同**：
   ```sql
   SELECT COUNT(*), COUNT(shipped_at), COUNT(*) - COUNT(shipped_at) FROM orders;
   --      3000       1420                 1580
   -- COUNT(列) 跳过 NULL —— "已发货数"就这么算出来的
   ```
2. **聚合会自动忽略 NULL，但 `COUNT(*)` 不会** —— 想数"有值的行"用列，想数"行数"用 `*`。
3. **GROUP BY 的列必须是分组键或聚合值**，`SELECT name, COUNT(*) FROM orders GROUP BY status` 在 SQLite 里能跑（随机挑一个 name）但在 PG 里直接报错 —— 宽松≠正确。

## 3.3 NULL 的三值逻辑：SQL 里最大的暗礁

逻辑学只有真/假，SQL 有**真/假/未知（NULL）**。先看实验：

```sql
SELECT NULL = NULL   AS "NULL=NULL",   -- NULL（未知！不是 1）
       NULL <> NULL  AS "NULL<>NULL",  -- NULL
       NULL IS NULL  AS "IS NULL",     -- 1（IS 专门用来问"是不是NULL"）
       1 + NULL      AS "1+NULL",      -- NULL（NULL 有传染性）
       COALESCE(NULL, 'fallback') AS "COALESCE";  -- fallback（提供默认值）
```

由"未知"推导出的两个必然结论：

**结论一：`WHERE x = NULL` 永远查不到东西**

```sql
SELECT
  (SELECT COUNT(*) FROM orders WHERE shipped_at = NULL)     AS 错误写法,
  (SELECT COUNT(*) FROM orders WHERE shipped_at IS NULL)    AS 正确写法;
--   0                      ← 一行都没有，而且不报错！
--   1580
```

`= NULL` 的结果是"未知"，WHERE 只放行"真"，于是**静默返回 0 行**。不报错是它最恶毒的地方 —— 你以为查完了，其实什么都查不到。

**结论二：`NOT IN` 的子查询里有一个 NULL，整个查询清零**（第 4 章实测）

实践守则：
- 判断 NULL 只用 `IS NULL / IS NOT NULL`
- 给 NULL 一个默认值用 `COALESCE(col, 0)`
- WHERE 里的条件优先写成"NULL 安全"的形式

## 3.4 日期函数：SQLite 的五件套

SQLite 没有独立的日期类型（TEXT/REAL/INTEGER 都能存日期），常用函数：

```sql
SELECT date('now'), datetime('now'), strftime('%Y-%m', '2024-11-11'),
       julianday('2024-11-11') - julianday('2024-11-01');
-- 2026-10-20 | ... | 2024-11 | 10.0
```

按月统计销售额（真实输出）：

```sql
SELECT strftime('%Y-%m', o.ordered_at) AS 月份,
       COUNT(DISTINCT o.order_id) AS 订单数,
       ROUND(SUM(i.quantity * i.unit_price * (1 - i.discount)), 0) AS 销售额
FROM orders o JOIN order_items i ON i.order_id = o.order_id
WHERE o.status IN ('paid', 'shipped') AND o.ordered_at >= '2024-01-01'
GROUP BY 月份 ORDER BY 月份 LIMIT 5;
```

```
┌─────────┬────────┬──────────┐
│ 月份    │ 订单数 │ 销售额   │
├─────────┼────────┼──────────┤
│ 2024-01 │    101 │ 653368.0 │
│ 2024-02 │     92 │ 443821.0 │
│ 2024-03 │    119 │ 710632.0 │
│ 2024-04 │     83 │ 579357.0 │
│ 2024-05 │    108 │ 683997.0 │
└─────────┴────────┴──────────┘
```

跨库对照：MySQL `DATE_FORMAT(d, '%Y-%m')`，PG `to_char(d, 'YYYY-MM')`，T-SQL `FORMAT(d, 'yyyy-MM')`（完整对照表在第 13 章）。

## 3.5 金额为什么不能用 REAL：一次实测

先看教科书案例：

```sql
SELECT 0.1 + 0.2,                      -- 0.30000000000000004
       0.1 + 0.2 = 0.3,                -- 0（假！）
       CAST(19.99 * 100 AS INTEGER);   -- 1998 ← 不是 1999！
```

`19.99` 的二进制浮点其实略小于 19.99，乘 100 得 1998.9999...，`CAST` 截断成 1998。**少了一分钱**。

再用 atlas.db 的 6048 条真实明细算总账：

```sql
SELECT ROUND(SUM(quantity * unit_price * (1 - discount)), 2)          AS "逐行ROUND后合计",
       SUM(CAST(ROUND(quantity*unit_price*(1-discount)*100) AS INTEGER)) / 100.0 AS "按分累加",
       ROUND(SUM(quantity*unit_price*(1-discount))
             - SUM(CAST(ROUND(quantity*unit_price*(1-discount)*100) AS INTEGER)) / 100.0, 4) AS 差额
FROM order_items;
```

```
18536759.5    18536759.98    -0.4845
```

**两种算法差了将近 5 毛钱**。在财务系统里这就是对账对不上的元凶。正确姿势（按严格程度排序）：

1. **整数存分**：`price_cents INTEGER`（首选，SQLite/MySQL 通用）
2. `NUMERIC/DECIMAL` 类型（PG/MySQL 支持，SQLite 存了也会退化成浮点）
3. 至少：聚合前 `ROUND` 到分，且**全程只用一种舍入策略**

## 3.6 常用过滤器速查

```sql
WHERE price BETWEEN 100 AND 200          -- 闭区间 [100, 200]
WHERE city IN ('深圳','广州','杭州')      -- 集合匹配
WHERE name LIKE '刘%'                    -- % 任意串，_ 单字符；以 % 开头无法用普通索引
WHERE note IS NOT NULL                   -- 判空
WHERE note <> ''                         -- 防空串
WHERE COALESCE(note, '') <> ''           -- 两者一起防
```

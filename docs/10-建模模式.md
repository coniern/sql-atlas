# 10 · 建模模式：真实业务里的七种难题

> 一句话：范式管不了的地方，靠模式库。这一章收集"每个业务系统都会遇到、教程却很少讲"的建模难题，全部给出可跑的方案与代价分析。

## 10.1 树形结构的三种存法（含 SQLAlchemy 官方示例的完整对照）

atlas.db 的品类用的是**邻接表**。但树还有两种存法，各有适用场景：

| 方案 | 表结构 | 查子树 | 插入/移动 | 适用 |
|---|---|---|---|---|
| **邻接表** | `parent_id` | 递归 CTE | O(1) | 层级浅、频繁移动 |
| **物化路径** | `path = '1/11/111'` | `LIKE '1/11/%'` | 要重写子树路径 | 读多写少（评论区） |
| **嵌套集** | `lft, rgt` 编号 | `BETWEEN lft AND rgt` | 移动一个节点重编号一半的表 | 几乎只读的巨型树 |

**物化路径实测**（不用递归也能查整棵子树）：

```sql
-- 给 categories 加一列 path：电子产品= '1', 手机 = '1/11', 配件 = '1/14'
-- 查"电子产品及所有子孙"：
SELECT * FROM categories WHERE path LIKE '1/%' OR path = '1';
-- 一次 B+ 树范围扫描，不需要递归 —— 这就是它的威力
```

代价在移动节点：把"电子产品"挪到"服饰"下面，它**整棵子树的 path 都要重写**。邻接表挪一个节点只改一行。

**决策口诀**：层级 ≤ 5 且会挪动 → 邻接表；万级节点只读 → 物化路径；真只读 → 嵌套集。（SQLAlchemy 仓库 `examples/` 里 `adjacency_list`、`materialized_paths`、`nested_sets` 三个示例目录就是这三种模式的官方实现，值得对照读。）

## 10.2 多对多与"带属性的连接表"

订单 ↔ 产品是多对多，落在 `order_items` 连接表。但真实业务马上要加"下单时的价格"：

```sql
CREATE TABLE order_items (
    item_id    INTEGER PRIMARY KEY,
    order_id   INTEGER NOT NULL REFERENCES orders,
    product_id INTEGER NOT NULL REFERENCES products,
    quantity   INTEGER NOT NULL CHECK (quantity > 0),
    unit_price REAL    NOT NULL,        -- ← 连接表上的属性：快照
    discount   REAL    NOT NULL DEFAULT 0
);
```

**判断标准：连接表上的属性描述的是"这次关联本身"（下单时刻的价格），不是两边任何一方。** 这种表已经不是纯连接表，而是独立的"事实表"——它是整个电商系统最值钱的表。

## 10.3 多态关联：一个 FK 指向多张表（能做但要小心）

需求：评论可以挂在"产品"或"文章"上：

```sql
CREATE TABLE comments (
    id         INTEGER PRIMARY KEY,
    body       TEXT NOT NULL,
    target_type TEXT NOT NULL CHECK (target_type IN ('product', 'article')),
    target_id  INTEGER NOT NULL      -- 指向 products.id 或 articles.id
);
```

代价（都要接受才可以用）：
- `target_id` **无法建外键** —— 引用完整性只能靠应用层 + 定期对账
- JOIN 要按 type 分支写
- 查"某产品被多少人评论"没问题，查"所有评论及其目标"要 UNION 两段

替代方案：拆成两张连接表（`product_comments` / `article_comments`），完整性全交给外键，代价是"查某人所有评论"要 UNION。**读多选多态，一致性敏感选拆表。**

## 10.4 EAV：终极灵活 = 终极失控

需求：商品属性千奇百怪（手机有内存、衣服有尺码）。EAV（Entity-Attribute-Value）：

```sql
CREATE TABLE product_attrs (
    product_id INTEGER NOT NULL REFERENCES products,
    attr       TEXT NOT NULL,
    value      TEXT
);
-- 查"内存≥8G 的手机"：
SELECT product_id FROM product_attrs
WHERE attr = '内存' AND CAST(value AS REAL) >= 8;
```

三个致命伤：类型全变成 TEXT、索引按 attr 分散效率低、"有哪些属性"没有约束（拼错一个词就是脏数据）。**除非做的是"属性完全用户自定义"的平台（像 SaaS 表单），否则用 JSON 列更可控**：

```sql
-- SQLite 3.38+ 内置 JSON 函数：
ALTER TABLE products ADD COLUMN specs TEXT;   -- 存 '{"ram": 12, "screen": 6.7}'
SELECT name FROM products
WHERE json_extract(specs, '$.ram') >= 8;
-- 还能建表达式索引：
CREATE INDEX idx_ram ON products(json_extract(specs, '$.ram'));
```

## 10.5 软删除：deleted_at 的坑

业务要"可恢复的删除"，标准做法是 `deleted_at` 时间戳而非物理 DELETE。但引入三连坑：

```sql
-- 坑①：每个查询都要记得加 WHERE deleted_at IS NULL，漏一处就泄漏
-- 坑②：UNIQUE 约束撞上软删除——用户改名后想用旧名，旧软删除行还占着唯一索引
--   解法：部分唯一索引（SQLite/PG 支持）：
CREATE UNIQUE INDEX idx_phone ON customers(phone) WHERE deleted_at IS NULL;
-- 坑③：外键指向软删除行算不算违规？——业务问题，没有标准答案，必须团队约定
```

## 10.6 乐观锁 vs 悲观锁：并发更新的两种答案

库存扣减，两个请求同时改同一行：

```sql
-- 悲观锁：先锁再改（PG: SELECT ... FOR UPDATE）
BEGIN;
SELECT stock FROM products WHERE product_id = 3 FOR UPDATE;  -- 锁住这行
UPDATE products SET stock = stock - 1 WHERE product_id = 3;  -- 等锁的请求排队
COMMIT;

-- 乐观锁：不锁，用版本号检测冲突（推荐——高并发下吞吐高得多）
UPDATE products
SET stock = stock - 1, version = version + 1
WHERE product_id = 3 AND version = 7;      -- 版本不对 = 有人改过了 → 影响行数 0 → 重试
```

判断标准：冲突概率高、事务短 → 悲观；读多写少、冲突罕见 → 乐观 + 重试。

## 10.7 快照与缓变维（SCD）

第 1 章讲过 `order_items.unit_price` 是快照。推广一下，这是"缓变维"问题：

| 数据 | 存什么 | 例子 |
|---|---|---|
| 事实（不变） | 快照值 | 下单时价格、收货时地址 |
| 状态（会变） | 引用 + 时间线 | 当前等级、当前库存 |
| 历史（要追溯） | 变更日志表 | 价格调整记录 |

**判断口诀：这份字段描述的是"当时"还是"现在"？** 当时的进快照，现在的做引用，追溯的开日志（atlas.db 的 audit_log 就是日志模式的最小实现）。

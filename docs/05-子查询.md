# 05 · 子查询：标量、IN、EXISTS 与改写

> 一句话：子查询是"先算出一个中间结果再往下查"。90% 的子查询可以改写成 JOIN 或 CTE，改写的标准只有一个：可读性。

## 5.1 四种子查询形态

```sql
-- ① 标量子查询：结果必须恰好 1 行 1 列，用在任何"一个值"能出现的地方
SELECT name,
       (SELECT ROUND(AVG(price),2) FROM products)          AS 全店均价,
       ROUND(p.price - (SELECT AVG(price) FROM products),2) AS 与均价差
FROM products p LIMIT 3;

-- ② 行构造子查询
SELECT * FROM orders
  WHERE (customer_id, status) = (SELECT customer_id, status FROM orders WHERE order_id = 500);

-- ③ 表子查询（FROM 里的派生表）：必须起别名
SELECT city, 均价 FROM
  (SELECT city, ROUND(AVG(credit_limit),0) AS 均价 FROM customers GROUP BY city) t
WHERE 均价 > 0 ORDER BY 均价 DESC LIMIT 3;

-- ④ 相关子查询：里层引用了外层的列 → 对外层每一行执行一次（性能敏感！）
SELECT p.name, p.price
FROM products p
WHERE p.price > (SELECT AVG(price) FROM products WHERE category_id = p.category_id);
```

④ 是双刃剑：逻辑直观（"比同类平均贵的产品"），但对大表是 N 次子查询。现代优化器很多能把它改写成 JOIN，**但别赌** —— 用 `EXPLAIN` 验证（第 9 章）。

## 5.2 IN vs EXISTS：什么时候等价，什么时候不等价

| 场景 | IN | EXISTS | 结论 |
|---|---|---|---|
| 子查询无 NULL，正向判断 | 等价 | 等价 | 都行 |
| 子查询可能含 NULL，**正向** `IN` | 安全 | 安全 | 都行（NULL 只影响 `NOT IN`） |
| 子查询可能含 NULL，**否定** `NOT IN` | **爆炸** | 正常 | **必须 EXISTS** |
| 子查询结果集巨大 | 可能先物化 | 通常半连接优化 | 看执行计划 |

一句话记忆：**`NOT IN` 唯一的适用前提是子查询列有 `NOT NULL` 保证；否则永远 `NOT EXISTS`。**（实测见 4.6 节）

## 5.3 相关子查询的经典用法：组内比较

"每个品类里最贵的产品"。传统写法要用相关子查询：

```sql
SELECT c.name AS 品类, p.name AS 产品, p.price
FROM products p
JOIN categories c ON c.category_id = p.category_id
WHERE p.price = (SELECT MAX(price) FROM products
                 WHERE category_id = p.category_id)
ORDER BY p.price DESC LIMIT 4;
```

窗口函数写法更清晰、只扫一遍（第 6 章细讲）：

```sql
SELECT 品类, 产品, price FROM (
  SELECT c.name AS 品类, p.name AS 产品, p.price,
         RANK() OVER (PARTITION BY p.category_id ORDER BY p.price DESC) AS rk
  FROM products p JOIN categories c ON c.category_id = p.category_id
) WHERE rk = 1 ORDER BY price DESC LIMIT 4;
```

> 经验法则：**"每组最大/最小/前 N"的题，2010 年后出现的数据库一律优先窗口函数。** 相关子查询留给"每组恰好一个标量阈值"这种窗口函数反而绕的场景。

## 5.4 子查询改写的三步法

拿到一条嵌套三层以上的查询：

1. **从最里层开始单独跑**，确认中间结果的行数和粒度
2. **把每一层包成 CTE**（`WITH t AS (...)`），给中间结果起业务名字 —— `WITH paid_orders AS (...)` 比 `FROM (SELECT ... ) x` 可读性高一倍
3. **检查有没有"该提前聚合的没聚合"** —— 粒度错位是复杂查询 90% 的 bug 来源（4.4 的膨胀就是这种）

```sql
-- 改写示例："2024 年下单≥3次且从未退款过的金卡客户"
WITH paid_2024 AS (                    -- 中间结果 1：2024 年有效订单
  SELECT customer_id, COUNT(*) AS n
  FROM orders
  WHERE status IN ('paid','shipped') AND ordered_at >= '2024-01-01'
  GROUP BY customer_id
),
refunded AS (                          -- 中间结果 2：退过款的客户
  SELECT DISTINCT customer_id FROM orders WHERE status = 'refunded'
)
SELECT c.name, c.city, p.n AS 有效订单数
FROM paid_2024 p
JOIN customers c ON c.customer_id = p.customer_id
WHERE c.tier = 'gold'
  AND p.n >= 3
  AND c.customer_id NOT IN (SELECT customer_id FROM refunded)  -- refunded 由 DISTINCT 保证无 NULL
ORDER BY p.n DESC LIMIT 5;
```

每一层都能单独跑、单独验证 —— 这就是 CTE 的核心价值：**把"一条巨查询"变成"几个可单测的小步骤"**。

## 5.5 子查询 vs JOIN：性能真相

老教程说"JOIN 更快"，在现代优化器面前大体过时了：

- PG/MySQL 8+/SQLite 都有**子查询物化/半连接改写**，多数场景计划相同
- 真正的性能分水岭是**相关 vs 非相关**：非相关子查询只算一次；相关子查询每行算一次，除非优化器能改写
- **用 EXPLAIN 说真话，别用 2010 年的经验写 2026 年的 SQL**

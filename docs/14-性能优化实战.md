# 14 · 性能优化实战：拿到慢查询的完整处理流程

> 一句话：优化不是背技巧，是一套流程 —— 先测量、再定位、后改写、最后验证。这一章把前面 13 章的知识拧成一条流水线。

## 14.0 全章案例：一条真实的慢查询

需求："2024 年每个城市的金卡客户数、订单数、销售额，按销售额倒序"。天真写法：

```sql
SELECT c.city,
       COUNT(DISTINCT c.customer_id)                          AS 金卡客户数,
       COUNT(DISTINCT o.order_id)                             AS 订单数,
       SUM(i.quantity * i.unit_price * (1 - i.discount))      AS 销售额
FROM customers c, orders o, order_items i          -- 反模式①：逗号连接
WHERE c.customer_id = o.customer_id
  AND i.order_id = o.order_id
  AND c.tier = 'gold'
  AND strftime('%Y', o.ordered_at) = '2024'        -- 反模式②：对列套函数
  AND o.status IN ('paid','shipped')
GROUP BY c.city
ORDER BY 销售额 DESC;
```

按下面的流程走一遍。

## 14.1 第一步：测量 —— 别猜，看计划

```sql
EXPLAIN QUERY PLAN <上面的查询>;
```

```
SCAN c                ← customers 全扫
SEARCH o USING INTEGER PRIMARY KEY (rowid=?)
SCAN i                ← 明细全扫（6048 行）
USE TEMP B-TREE FOR ORDER BY
```

两个 SCAN —— 每次执行都要扫 3000 + 6048 行。

## 14.2 第二步：定位 —— 三个改写

**改写①：日期函数 → 范围条件**（第 9 章：函数包列 = 索引失效）

```sql
-- strftime('%Y', o.ordered_at) = '2024'
--    ↓ 改成范围，索引才有用武之地
o.ordered_at >= '2024-01-01' AND o.ordered_at < '2025-01-01'
```

**改写②：逗号连接 → 显式 JOIN**（可读性 + 防笛卡尔积）

**改写③：先聚合再 JOIN**（第 4 章：粒度对齐）

```sql
WITH sales AS (                       -- 先在明细层聚合到"订单"粒度
  SELECT order_id,
         SUM(quantity * unit_price * (1 - discount)) AS amt
  FROM order_items
  GROUP BY order_id
)
SELECT c.city,
       COUNT(DISTINCT c.customer_id)  AS 金卡客户数,
       COUNT(o.order_id)              AS 订单数,
       ROUND(SUM(s.amt), 0)           AS 销售额
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
JOIN sales  s ON s.order_id   = o.order_id
WHERE c.tier = 'gold'
  AND o.ordered_at >= '2024-01-01' AND o.ordered_at < '2025-01-01'
  AND o.status IN ('paid','shipped')
GROUP BY c.city
ORDER BY 销售额 DESC
LIMIT 5;
```

```

│ city │ 金卡客户数│ 订单数 │ 销售额    │
├──────┼──────────┼────────┼───────────┤
│ 重庆 │        5 │     55 │  416816.0 │
```

## 14.3 第三步：加索引 —— 按查询模式设计

这条查询的访问路径是：`customers(tier)` → `orders(customer_id, ordered_at)` → `sales(order_id)`：

```sql
CREATE INDEX idx_customers_tier   ON customers(tier, city);
CREATE INDEX idx_orders_c date    ON orders(customer_id, ordered_at);   -- 等值在前（第 9 章口诀）
CREATE INDEX idx_sales_order      ON sales(order_id);                   -- 物化表也要索引
```

验证：再跑 EXPLAIN，确认 SCAN 变 SEARCH。**每加一个索引都要实测前后耗时**，写不进报告的优化等于没做。

## 14.4 第四步：验证 + 回归

优化清单（按投入产出排序）：

```
①  改写 SQL（成本：0，收益经常最大）
    - 函数包列 → 范围条件
    - 先聚合再 JOIN
    - NOT IN → NOT EXISTS
    - SELECT * → 只取需要的列（配合覆盖索引）

②  建索引（成本：写入变慢，收益巨大）
    - 外键两侧都有索引
    - 复合索引：等值在前，范围在后
    - 热点查询上覆盖索引

③  数据库参数（成本：0）
    - ANALYZE 更新统计信息
    - WAL 模式 + busy_timeout（SQLite）

④  结构性方案（成本高，最后考虑）
    - 物化汇总表（定时/触发器维护）
    - 读写分离、缓存层
    - 换 OLAP 引擎
```

## 14.5 一份自查清单（贴在工位上）

```
□ WHERE 里有对列套函数/运算吗？
□ JOIN 的两边（尤其外键）都有索引吗？
□ SUM 的粒度和 JOIN 后的行粒度一致吗？（4.4 膨胀）
□ NOT IN 的子查询可能含 NULL 吗？
□ 分页是深分页吗？（LIMIT 100000,10 → 游标分页）
□ COUNT(DISTINCT x) 能不能换成预聚合？
□ 大事务里有没有 RPC/循环单条 INSERT？（改批量）
□ EXPLAIN 里有 SCAN 大表 / TEMP B-TREE 吗？
□ 改动前后各测过一次耗时吗？（有数字才能上线）
```

## 14.6 什么时候不该优化

- **查询一天跑一次、300ms** —— 别动它，去写新功能
- **数据量 1 万行、SCAN 也才 5ms** —— 加索引是负优化（写放大 > 读收益）
- **业务逻辑还没稳定** —— 先让正确性落地，性能问题等画像清晰了再治

> 性能优化的第一性原理：**先测量，再动手；每次只改一处，保留对照。** 不能证明"变快了"的改动，默认回滚。
